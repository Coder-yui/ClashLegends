# 模型库存：首轮需求、旧储备与构造能力

MatchResourcePlan负责资源/技能可达；MatchModelDemand分开输出首轮事件预算、明确保留的旧有限储备、初始库存及构造能力。它们不修改经济、20Hz、手牌、出生或活体数量。当前结论与边界见[本阶段交付](deliveries/2026-10-18_preload_model_inventory.md)。

## 数量的三个层次

| 层次 | 当前实现与限制 |
| --- | --- |
| 资源可达 | 双方真实decks、已选技能、衍生/形态/阵营路径、死亡替身；不把整个闭包当作独立出牌根 |
| 首轮事件预算first_burst | 每牌组来源一次部署，完整deployment_count及重复spawn_plan成员；一次被动批次、一次选定主动批次、亡语/转换事件；镜像另算一次真实可复制来源，普通席镜像没有主动；系统每阵营每种首波两路2份 |
| 旧有限储备legacy_reserve | 对尚无更紧并发证明的路径保留旧2份基础、一次来源引用量×2及旧32/64缓存政策；系统每种/每侧独立4份；不再把“两代×两批×全部主动次数”叠乘 |

first_burst是逐来源首轮事件的保守合并预算，不称为所有合法短时序列上界、数学最小数量或整局最大存活数。生命周期max_uses只记录资格/重复间隔信息，不直接乘成同时活体需求。持续生产、奖励加速轮转、长时间存活和转换仍可能耗尽储备。

同一来源互斥形态/成长/费用升级同path取max，独立来源和双方相加；重复部署成员不去重。系统不受镜像翻倍，但牌组直接单位/编队与系统共享path时独立相加。Unit._die的死亡替换会跳过原身体死亡表现；复活、死亡替换及其后续同path不再额外叠加原身体，保留真实死亡替身路径及采样配置。

保留容量=`max(first_burst, legacy_reserve)`；step-bind初始=`max(first_burst, ceil(legacy_reserve/2))`，loading-only初始为完整有限储备。旧32/64仅显式保留为缓存政策，不能截断first_burst或合法战斗单位；不是单卡/整局需求证明。没有旧主模型spec的死亡替身沿用原独立场景2份储备，并由首轮事件预算补足。

无模型消费的buff由每模型bank持有，预部署由独立消费者创建；这些场景保留原绘制样本，独立池库存为0。塔/水晶、弹体和动态特效内部模型不属于这里67个主模型/死亡替身路径的构造声明覆盖。

## 开发计划门禁

MatchResourcePlan在Main读取模型资源之前运行纯定义门禁；错误进入原准备失败入口。声明批次/成员数>64、引用深度>8、图访问>512、嵌套/合并首轮单path>128、首轮总量>256、保留总量>512明确报开发审阅错误，不截断数据或丢弃战斗单位。它们是当前项目的开发审阅预算，不是512实例可安全装入任意设备的保证；超出应先审阅数据/构造计划，不能静默放宽或cap。

一般生产自环/互环拒绝。当前有界例外依据数据语义：死亡替换与复活返回时charges=0的双向关系，以及有限主动生成自身且子体不继承主动。其余未来循环须扩展明确有界合同。先检查批量与复杂度，再展开数量，避免巨大嵌套乘法占用开局内存。新卡延续部署/衍生数据合同及构造声明，不增加中央英雄数量名单。

## 构造声明与补货

场景根必须有显式合同，例如：

```ini
metadata/model_pool_construction = {"version": 1, "mode": "loading-only", "scripts": []}
```

mode只接受loading-only/step-bind；未知或缺失声明明确失败。step-bind的scripts必须匹配实际入树节点脚本目录，源码或构造内容改变要重新审阅，目录匹配本身不是成本证明。没有明确能力的包装保留loading-only，不能因模板存在自动许可。

当前67路径中37个纯场景、奥恩及本批审阅的女皇/赛恩/两纳尔/两鱼共44个为step-bind，剩余23个仍未知能力、完整预建旧有限储备。新增六路径与ModelTemplateView共用构造：查找节点/动画、查询模板、挂载共享网格或保留原网格引用；没有_ready网格加工、材质复制或modifier创建。动态动作/出生效果仍属实例状态和后续效果热点，不能用这次构造审查宣称它们零分配。六路径各一活体定向验证了构造、重复准备和分步绑定，未做全硬件成本保证。

局中只补回`min(initial_capacity, capacity)`闲置目标。capacity明确为闲置缓存上限，与原回收判定一致；活跃模型由消费者持有，不计入闲置补货额度，否则活体达到capacity时会永久断粮。活跃+闲置因此可能超过capacity，闲置仍受capacity限制、单次最多一个半成品；这是补货内存语义的明确调整，不能把静态容量表当成局中总模型上限或内存收益。

补货以SceneTree.process_frame起点到调用时的墙钟衡量已发生的主线程工作，排除帧率上限等待；不再把16.7/33.3ms帧间隔当作CPU工作。它不包含起点前物理、调用后的其他节点或GPU成本，不是完整帧预算预测。已发生工作≥8ms时最多连续退让3帧，再允许一个最小步骤；单步>1ms后冷却1～3帧。即使持续超载也只有限退让，最多7个观察帧推进一步，不永久停止补货。每个真实帧至多一步，同帧重复调用不再推进；完整任务结束后轮转路径，热路径不能反复抢占。任务内绑定clip数有限，但没有逐step跨路径抢占。

构造/入树、包装、begin_bind、单clip分阶段，不在本帧循环补完。单个引擎操作不可抢占，1ms是目标而非硬上限；长步骤、前台退让和每path最长wall分别记录，不据一次波动更改能力/数量。取消立即clear半成品owner、释放节点并断开process_frame信号，release再清观察器。计划内耗尽仍同步构造完整动画和严格材质闭包，记录miss/exhausted/最长同步耗时；不丢合法单位。**有限恢复不等于补货吞吐一定赶上任意合法生产，长期与完整对局流畅仍未证明。**

局中补货任一步失败现在先取消、释放半成品并断开帧信号，再经pool.resource_failed → BattlePresentation → Main只报告一次；后续帧不再重试。`python3 tools/maintenance/model_inventory_revision.py --mode failures`用小夹具检查四个失败阶段、后续8帧不重建及死亡替身null的原错误传播，38项通过，不运行对局/效果/渲染。现有沙盾两个辅助源码pin经明确审阅续记，必要增量生成及独立check均已恢复一致；状态见[集成修订](deliveries/2026-10-18_preload_mechanism_analysis.md#2026-10-19三处集成修订当前)。

## 当前窄验证入口

`python3 tools/maintenance/model_inventory_revision.py`默认只执行全定义/技能选择账单、开发门禁和MatchLoadingSuite；1770是断言数，覆盖82个定义/技能代数输入，不是1770个场景或合法对局组合。`--mode capabilities`顺序检查六个审阅模板构造，每次一个实例。`--mode scheduler`用虚拟frame/work/step时钟检查稳定16.7/33.3ms、偶发与持续超载、超时冷却、同帧去重、任务轮转、活跃额度及真实取消信号清理，不加载模型。`--mode compile-runtime`只编译轨迹；`--mode runtime`实际用MatchRuntime出牌、命令缓冲、部署资格、主动、周期召唤与伤害亡语驱动有限消费，不自动重试。

实际Runtime仅准备账单要求的墓碑2份、雾行者8份（闲置容量16），走生产库存helper、UnitModel3D工厂；权威夹具不运行系统兵线/UI/音频，不是完整场景启动或渲染验收。首轮旧调度结果8命中/2缺货、129慢帧跳过、0补货、最长同步创建2372μs保留为失败边界。调度修正后仅复验一次同牌组/钱包/真实30FPS输入：雾行者10命中/0缺货、补货完成6、62步最长659μs，前台退让2帧、0超预算；不增加初始库存，不人为更换delta。43项纯调度检查与本次33项真实轨迹分别记账，不能据此保证所有路径吞吐或整场性能。已撤回旧手写事件消费工具，源码和失败/成功证据保留本地素材库；新结论不累加首版3205/84/80/47等旧断言。
