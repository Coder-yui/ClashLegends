## 2. 总体评价

工程已经不是只有可玩场景的原型。卡牌定义、固定步长模拟、表现代理、控制与攻击状态、音频生命周期、内容契约、工作台和文档导航都已经存在。主要问题不是“完全没有架构”，而是：**一些边界已经建立，另一些仍靠 Main 与跨模块私有字段访问维系；正常路径比异常顺序和结束路径更完整；验收结果还不能可靠绑定版本。**[S03][S04][S05]

| 维度 | 判断 | 当前最有价值的动作 |
| --- | --- | --- |
| 总体方向 | 可以保留 | 继续以 2D 权威模拟、3D/音频表现为骨架 |
| 模块职责 | 部分明确，仍有集中耦合 | 收敛生命周期、网络适配和工作台边界 |
| 新卡接入 | 已有可复用入口 | 补字段域约束和“只改表现不改规则”的自动测试 |

| 联机完整性 | 高优先级风险 | 修实体生命周期、终态同步、会话与请求授权 |

### 应明确保留的设计

**固定模拟与表现分离。** `FixedStepClock` 保留累计时间；单位战斗通过固定 Tick 推进，3D 模型是代理而不是权威物理对象。这条主线是对的。不要因为存在局部越界而否定整个方向。[S06][S07]

**逐卡定义与递归只读。** `CardDB` 集中注册并编译定义，运行期避免修改共享数据，主动技能取运行副本。对多次 AI 修改尤其有价值。[S08][S09]

**动画不是简单 play/idle 切换。** 当前有动作优先级、连续攻击末帧保持、序列动画、晚到动作按权威进度对齐、控制覆盖及每实例动画库副本。维护套件还检查了动画/材质隔离。不要“优化”掉副本却重新引入共享资源污染。[S10][S11]

**声音已有生命周期。** 播放器池、动作/Buff 持续声分层、来源跟踪、暂停恢复和销毁清理均已实现。音频问题应在现有框架内修，而不是重新到处添加播放器。[S12][S11]

**导航和碰撞已有细分语义。** 部署格占位、实际圆柱体积、地形阻挡、空地层和动态阻挡引用计数不是同一件事，当前代码已经体现这些区分。[S13][S14]

**工具和文档不是空架子。** 工作台、维护审计、测试编排、任务导航、新卡清单和素材来源规则都已经有用；下一步应提升证据可信度，而不是继续堆更多入口文档。[S02][S03][S15][S16]

## 4. 五项优先正确性修复

### CL-01：换弹体外观可能改变战斗规则

**位置：** `scripts/battle/projectile_system.gd`，`launch()` 与 `tick()`；代表配置 `scripts/data/cards/ashe.gd`。[S17][S18]

`launch()` 根据 `projectile_visual` 决定是否把实际弹体起点向前移动，并按视觉名称选择不同的 `radius`。`tick()` 又把这个 `radius` 用在真实命中判断中。因此，视觉名称不是单纯选择箭、球或针的画法，它也能改变发射起点和伤害触发时刻。

这对当前协作方式风险很高：用户提出“把箭换成更漂亮的模型”，AI 若只改看似表现的配置，也可能悄悄改变战斗结果。艾希定义中，一些带 `visual` 名称的字段目前还放在 `gameplay` 中，更说明四域命名本身没有保证规则隔离。

**修复边界：** 显式定义权威字段，例如发射起点偏移、碰撞半径、速度与最大飞行距离；表现字段仅控制模型、绘制高度、材质、视觉偏移。先把现有隐含数值迁移为显式值，保持当前实际命中行为，再拆依赖。不能顺便把所有弹体统一半径或起点，造成未授权平衡调整。

**必须增加的回归：** 给定相同初始状态、输入、目标移动轨迹和随机种子，仅替换弹体视觉、音频与模型配置，比较每次命中 Tick、伤害、目标生命及击杀结果。允许视觉轨迹不同，不允许权威结果变化。应覆盖普通远程、建筑弹体、扇形技能弹体。

**完成条件：** 权威发射与命中函数不再按视觉名称决定几何规则；迁移前后的基线战斗结果保持一致；纯表现替换测试通过。

### CL-02：生成事件与快照之间存在生命周期竞态

**位置：** `main.gd::_rpc_spawn_unit()`；`network_snapshot_system.gd::apply()`、`_apply_units()`、`_unit_snapshot_payload()`。[S19][S20]

快照应用有版本、长度和 Tick 检查，这是优点。但单位生命周期处理仍有缺口：可靠 Spawn 创建单位；快照中找不到本地对应单位时直接跳过；本地有、当前快照没有的单位则被删除。Spawn 没有携带出生 Tick 或实体生命周期版本，普通快照也不包含完整重建描述。

可构造如下反例，注意这不是“已经在本机复现”的声明：

| 顺序 | 客户端收到的内容 | 当前实现的结果 |
| --- | --- | --- |
| 1 | 已接受快照 Tick 90 | 时钟为 90 |
| 2 | 可靠 Spawn：主机在 Tick 101 创建单位 X | 本地生成 X，但未建立出生 Tick 屏障 |
| 3 | 延迟到达的快照 Tick 100，其中还没有 X | 100 大于 90，被接受；X 因缺席被删除 |
| 4 | 后续 Tick 102 快照包含 X | 本地找不到 X，直接跳过；不能恢复 |

Godot 的默认 channel 0 也会按传输模式分成独立通道；不能把“可靠 Spawn”和“不可靠快照”理解成一条全局有序消息流。仅把快照改为 `unreliable_ordered` 不能解决跨模式生命周期问题。[G01]

**修复边界：** 引入会话标识与实体出生/销毁的时间或版本；删除规则必须知道某快照是否有资格判断某实体的存在；提供重建或全量重同步路径。可靠销毁标记、带出生描述的实体同步或专门重同步协议均可，先选最小闭环，不必同时实现所有方案。

**回归场景：** Spawn 先到而旧快照后到；快照先到而 Spawn 后到；丢一份快照；重复 Spawn；重复销毁；上一局消息晚到；快照发现未知实体。测试应重放真实序列化数据和生命周期事件，而不只直接写本地字段。

**完成条件：** 所有乱序场景最终收敛到主机实体集合，且不能把下一局对象误认成上一局对象。

### CL-03：终局状态与战斗声音没有统一收尾

**位置：** `main.gd::_process()`、`_end_game()`、`_rpc_end()`；`network_snapshot_system.gd::_apply_towers()`；`active_skill_effect_system.gd::tick_visuals()`；`game_audio_manager.gd`。[S21][S22][S12]

主机发送快照后才推进模拟；若本次模拟产生致胜一击，`game_over` 随即为真，以后主机主循环提前返回。结束 RPC 主要传结果文字，而不是可靠的最终战斗状态。客户端塔的生命与摧毁表现又依赖快照应用，因此最后一次致胜伤害可能不再有机会同步给客户端。

另一条路径是音频：音频管理器有退出树清理，但终局并不等于退出场景。动作/Buff/区域/飞行音可能仍持有运行状态。区域音频倒计时甚至由技能表现更新调用，主机结束后停止这条更新，不能依靠计时自然结束。声音是否需要淡出、是否保留环境声属于设计选择，但必须有明确终局策略。

**修复边界：** 设计一个幂等的结束入口，可靠传送 `session_id、final_tick、winner_team、reason、terminal_state` 或等效结构。客户端先接受最终状态，再进入结束表现；旧快照不得覆盖终态。终局统一拒绝新命令，关闭需要关闭的战斗持续声和飞行声，处理区域、等待中的效果与 UI。不能只补发一次不可靠快照。

结果协议应使用队伍和原因，而不是让客户端根据中文“胜利/失败”字符串推导语义。界面文案放在显示层。

**回归场景：** 快照刚发送后的一击致胜；双方都在播持续技能时终局；有未命中弹体和固定区域时终局；重复结束通知；终局后旧快照晚到；返回菜单后再开一局。

**完成条件：** 双端最终生命、摧毁状态和胜负一致；结束后没有不应保留的战斗循环声；重复收尾不产生重复节点或重复播报。

### CL-04：联机会话与请求来源限制不足

**位置：** `main.gd::_start_host()`、`_on_peer_connected()`、`_rpc_register_deck()`、`_rpc_deploy_request()` 及主动请求入口。[S23][S24]

连接回调直接进入开局流程，未见对“唯一对手”和“已开局”的完整保护。卡组注册检查卡组内容，却未限制为绑定的对手、合法的大厅阶段和一次性确认；注册后会初始化对方手牌循环。部署请求取得发送者 ID，主要用于回复，但没有在这条入口把发送者与获准控制的队伍绑定。

这同时是正确性和防误用问题。`any_peer` 只说明远端可以调用，不代表业务上已经有权修改某队伍的状态。[G01]

**修复边界：** 为当前一对一游戏建立小型 Session 状态机：大厅 → 加载 → 运行 → 结束/断线。绑定唯一对手与队伍；双方卡组和必要内容版本在运行前确认；禁止局中通过注册入口重置手牌；重复回调要幂等；超额连接不得重启比赛。断线至少要有明确停止、提示和安全退出，不要求现在实现复杂重连服务。

**回归场景：** 第三方连接现有对局；对手重复注册卡组；局中重注册相同卡组；非参与者请求部署/技能；双方加载速度不同；协议或规则内容版本不同；连接失败与中途断线。

**完成条件：** 所有影响权威状态的网络入口都能回答“谁、在哪个会话阶段、允许控制哪个队伍”；禁止的请求不能改钱、手牌、实体或比赛阶段。

### CL-05：建筑在命令缓冲内可通过同一空位校验

**位置：** `main.gd::play_card()` → `_deploy_card()` → `_tick_pending_card_deployments()` → `_execute_card_deployment()` → `_spawn_card_units()` → `_spawn_unit()`。[S25][S26]

当前位置合法性在请求被接受时检查；命令随后进入固定延迟队列。最终执行和建筑生成没有重新检查占位，也没有把已接受、尚未生成的建筑位置登记为预留空间。最终 `_spawn_unit()` 的落点安全修正针对地面移动单位，明确不包括建筑。

因此，两条在建筑实际生成前到达的合法建筑命令，可以都看到同一空位并被接受。后续两条命令直接生成建筑。这是时间上的竞争，不需要多线程才会出现。

**修复边界：** 最简单是接受建筑命令时预留占位；同时为到期执行时环境变化定义策略。需要明确区分“预留部署格”“真实障碍”与“已部署实体”，避免尚未落地的建筑错误阻挡行军。取消、断线、终局和失败必须释放预留。

执行失败是否退款、是否恢复手牌、是否允许自动挪位属于玩法决策，不能由重构自行决定。建议预留与执行重验组合，不建议临时悄悄挪到另一个玩家没有选的位置。

**回归场景：** 两张不同建筑连续选择相同落点；带预部署的建筑；塔墟条件改变；队列取消；旧局命令残留；同一命令重复投递。

**完成条件：** 命令接受、扣费、手牌变更、占位和生成有一致结果；失败路径不留下错误占位或未解释的资源损失。

## 5. 结构、分层与复用

### CL-06：已经拆了文件，但还有“通过 Main 串回去”的耦合

`BattleContext` 替代了任意查找当前场景，这应保留；但它仍绑定 Main 并转发其状态。若干系统持有 `_controller`，访问 Main 的私有字段；技能表现计时调用音频管理器的私有 `_tick_zone_audio()`；工作台重建场景还会直接遍历音频管理器子播放器并停止它们。这些是实际的所有权边界问题，而非目录美观问题。[S22][S27][S28]

建议遵循一个简单标准：**拥有状态的模块，同时拥有更新、清理和恢复该状态的方法；别人只发请求或读取公开快照。**

| 边界 | 建议职责 | 不应承担 |
| --- | --- | --- |
| Main / 启动装配 | 创建节点、接线、进入对应模式 | 持有所有系统的内部计时和容器细节 |
| MatchSession | 会话阶段、队伍/对手、开局/终局/断线 | 模型和音效播放细节 |
| 命令服务 | 校验、身份、费用、排程、取消结果和占位事务 | 鼠标 UI、音频子节点管理 |
| 战斗系统 | 命中、移动、状态、生成/销毁意图 | 按素材名称决定规则 |
| 网络适配 | 编解码、RPC、版本与生命周期传输 | 根据 UI 文案判断胜负 |
| 表现与音频 | 消费只读表现状态、语义事件，管理本层生命周期 | 回调真实伤害、改变权威碰撞 |
| WorkbenchController | 测试场景编排与验收工具操作 | 混入正式玩家资格的隐藏特殊分支 |

不要求立即创建上述所有新类。先从当前真正发生的问题所在边界抽取。已有 `ProjectileSystem` 的信号是可沿用的模式；不必增加一个所有模块都可随意发布任意字符串的全局事件总线。

**网络拆分约束：** Godot 高层 RPC 应保留在 Node 派生对象上，且两端 NodePath 和 RPC 定义要一致。不能把 RPC 为了“变薄”直接移进 RefCounted；可以让薄 Node 适配层调用可测试的服务。[G01]

### CL-07：Unit 与动画代理按职责拆，不按行数拆

Unit 当前包含部署、索敌、攻击、击退、控制、变形、资源、Buff、护盾、死亡相关逻辑与网络/表现读取。UnitModel3D 包含动作仲裁、攻击分段、动作序列、控制覆盖、模型替换、特效材质和挂点同步。它们的体量反映真实功能，不等于应该机械切碎。[S10][S29]

建议按以下顺序收敛：先把状态所有权清楚且已有雏形的 ControlState、AttackTimeline 用稳定接口接好；再处理主动施法/形态过渡和生命/护盾等一组有共同规则的状态。动画层优先分开“选择当前动作”“播放序列及对齐进度”“模型与材质生命周期”。Unit 可以继续作为 Godot Node2D 实体，不必为了纯逻辑架构把整个游戏脱离场景树。

**不要做的事：** 新英雄就复制一个 Unit 子类；把每个十行函数拆一文件；迁移后仍全部传 Main，导致依赖关系原封不动；删除已支持的冻结、眩晕、晚到对齐或双向变形以换取代码简短。

**验收准则：** 接一张只复用现有机制的新卡，通常修改该卡定义、素材/包装、手册与必要契约，不需要同时改 Main、Unit 和音频/动画通用状态机。确需新增机制时，应能指出唯一主要归属模块及其回归。

## 6. 数据、命名与文档

### CL-08：把“四域结构”升级为“可检查的域契约”

现有定义按 gameplay、visual、card_art、audio 编写，但编译会把部分域合并到平铺字典。域类型检查、已有的 CARD_FIELDS/AUDIO_FIELDS 等字段白名单和递归只读都应保留；仍需把跨域同名冲突与字段归属在编译前明确检查。全局字段合法不等于它放在任意域都合法。平铺兼容本身不是错误，但不能把这个编译方式当成已经实现了强分层。[S08][S18]

具体校验器风险：音频配置中，某些 `attack_launch_until_impact` 分支会先对 `events` 调用字典方法，后面才检查 `events` 的类型。对错误类型的输入，校验器可能先产生脚本错误，而不是返回一条可读的内容错误。[S30]

建议验证顺序固定为：类型 → 必填与形状 → 数值范围及有限性 → 资源与引用 → 跨字段语义 → 能力与真实消费者。错误消息带 card_id、完整字段路径、期望类型和实际值。异常输入测试既检查“报了错误”，也检查“没有抛出/打印脚本运行错误”。

不要求全部改成 Godot Resource。可先保留字典定义，增加可靠编译和契约；对于命令、生成请求、命中结果和网络实体描述等频繁跨模块传递的数据，再采用小型强类型对象，减少多位置参数与拼错键名风险。

### CL-13：文档总体可用，但“发射”和“命中”不能混写

艾希数值手册把主动技能列成“开始后命中时间 0.16 秒”，同时写“开始后发射时间 0.16 秒”和飞行时间。实际实现是在效果节点发射真实弹体，之后由弹体碰撞结算命中。因此，0.16 秒不能无条件描述为目标受伤时刻。[S18][S31][S32]

应统一以下术语：

| 术语 | 应表达的含义 |
| --- | --- |
| 命令接受 | 校验成功并进入缓冲，不等于开始播放技能 |
| Cast Start | 施法真正开始及资源快照锁定 |
| Release / 发射 | 箭矢、弹体或区域正式产生 |
| Effect Execution | 直接效果执行节点；可能只是发射弹体 |
| Collision Impact / 命中 | 目标实际受到判定和结算 |
| Recovery / 收招 | 行为或动作恢复阶段 |
| seconds / ticks | 分开注明，避免把渲染帧、模拟 Tick 和秒混用 |

`elixir` 与界面“金币”、`art_dev` 与工作台、各种 ability/active_skill 命名也应形成一个小词汇表。可以逐模块清理内部命名，但稳定 card_id、网络身份、来源事件名和资源路径不是随意重命名对象。源音频的长事件名承担溯源作用，不应为了短而丢失身份。

**数值文档策略：** 用户手册保留中文说明、设计意图和例子；基础数值表可以由工具生成局部片段，或做只读差异检查。不要把整篇手册覆盖成程序字段清单，也不要强行要求所有叙述完全自动生成。[S03][S15]

## 7. 动画、音频与效果规则

### 已有能力应继续用，而不是再造一套

动画动作优先级和权威时间对齐已有实现；控制状态通过统一表现状态消费；形态替换不新建权威 Unit；攻击来源与出手形态可在弹体在途时保留。这些都在解决实质问题。[S10][S11][S17]

下一步测试重点应转向**组合**：攻击前摇中眩晕、技能中冻结后解除、冻结与眩晕重叠、控制期间死亡、变形边界命中、出手后来源销毁、技能动作/Buff 长音同时存在、终局/切页/退出清理。已有套件覆盖了其中一部分，应补差集而不是另建重复套件。[S11]

### CL-11：叠加和取消规则先写清，再决定是否改实现

ControlState 明确采用最长持续时间和最强倍率，不为每个来源独立计时。这是已声明的聚合规则，不应误判为必然错误。[S33]

护盾行为更需要确认：`add_shield()` 累加盾量、取最长时长，但把衰减速率改成最后一次添加的速率。非衰减盾可能把已有聚合盾的衰减停止；衰减盾加入后则按最新速率处理整个聚合池。是否接受这种先后顺序依赖，需要单独定义。[S34]

主动技能还存在“入队时扣费、到期时重新判断合法性”的路径；死亡、控制、资格被新实例替换或其他原因取消时，队列如何处理费用也应有单一规则。当前读到的失败/取消路径没有统一退款事务，但这是否是错误，取决于项目是否有意采用提交即付费。[S35]

建议形成短小的规则矩阵，而不是现在引入万能 Buff 框架：多个护盾是独立层还是合并池；强弱 Buff 是否继承时间；控制打断还是暂停；技能接受后死亡如何扣费；终局撤销如何清理。先给当前行为写特征测试，未经产品决定，不改变平衡。

### CL-15：音频拥挤时的策略需要实听和预算

短音播放器池与持续声上限已有实现，但满池时的轮转/淘汰不能充分表达重要性。未来单位和技能更多时，可能让重要命中/播报与普通连续战斗声互相挤占。应按类别和重要性设定保留、替换或虚拟化策略，并记录被丢弃/被打断次数，而非直接把池无限放大。[S12]

此外，团队覆盖配置已有统一入口，但部分事件路径仍直接读取形态内 audio。应在启用新的 team_overrides 内容前测试所有入口是否同样遵循规则；本次没有确认某个现用音频因此实际错误，属于契约一致性检查项。[S12][S36]

## 8. 测试、规范与可复现交付

### CL-09：让“通过”成为可靠事实

`tests/mechanics_check.gd` 已有统一编排，维护套件也验证了只读数据、攻速缩放、资源依赖、音频分层、模型隔离和部分网络表现。不能说项目没有测试。[S02][S11]

但 runner 的主要失败累计来自 `_expect()`；文档也提醒退出 0 不够，还必须看最终汇总及 SCRIPT ERROR。对于用户不读代码的协作方式，把日志人工筛错作为最后防线仍不够稳。[S02][S37]

建议保留现有入口，外面增加一个统一校验执行器，负责导入、审计、机制、必要联机、结果归档和超时清理。它应同时检查：进程状态、预期套件完成、最终结构化结果、没有意外脚本错误。不要把固定的历史断言数当永久门槛；应检查测试没有中途跳过或异常退出。

| 测试层 | 应覆盖 | 输出 |
| --- | --- | --- |
| 内容/架构契约 | 字段域、引用、真实消费者、资源、禁止依赖 | 卡牌/路径/字段级错误 |
| 逻辑测试 | 时钟、费用、目标、伤害、控制、护盾、状态转换 | 可单独运行的结果 |
| 场景集成 | 接受命令到生成、死亡、终局及清理 | 场景和断言日志 |
| 联机协议 | 编解码、乱序、缺失、重放、旧会话、最终状态 | 双端实体/结果一致性 |
| 表现契约 | 事件一次性、动作优先级、实例隔离 | 自动状态检查 |
| 人工验收 | 观感、音色、节奏、双阵营、形态、触屏 | 与版本绑定的证据 |
| 性能测试 | 完整对局、拥挤、生成峰值、设备持续运行 | 分位耗时、内存和网络数据 |

当前不少套件共享 Main 并直接操作内部状态。白箱测试对动画阶段与资源隔离有价值，不应全部删除；但要增加公共命令/真实编码数据的测试，并让关键套件可单独运行。共享场景需要可验证 reset，防止测试顺序污染。

现有联机冒烟步骤应封装成有超时、可配置端口、能捕获双方日志并清理子进程的执行流程；不能因为打印“已连接”就当同步完整性通过。

### 建议统一交付证据

每次验证至少记录：提交 SHA、工作区是否有未提交改动、引擎精确版本、执行命令、套件结果、日志位置、人工未验项。仅标 commit 不够：脏工作区运行结果不能冒充该纯提交的结果。条件允许时同时记录内容摘要或构建 ID。

推荐建立一个稳定入口，例如 `tools/verify.py`，但这是建议名称，并非当前已有命令。内部复用现有 `audit_project.py` 与 Godot 测试，不再复制一套逻辑。

`audit_project.py` 本身的只读定位合理：它检查链接、资源引用、Python 语法、UID、卡牌文档和素材队列污染；资源哈希报告只是候选，不应据此自动删除动态依赖和素材源件。[S16]

## 9. 最适合“用户提要求、AI 实现”的工程闭环

### CL-10：工作台应该成为验收凭证，而不只是预览器

当前工作台有模型、实战、音频与验收页面，状态信息也能显示攻击序号、进度和控制状态。这对不直接编写代码的项目负责人很有价值。[S38]

缺口在记录：检查状态放在会话内，导出主要包含卡牌、时间、诊断、勾选和备注；没有形成自动持久化、构建版本和依赖变更失效的闭环。文档已明确离开前需要导出，尚无跨会话恢复。[S15][S39]

建议按收益顺序补：自动保存、重新打开恢复、关联构建/提交与修改状态、记录场景/队伍/形态、保存截图或录音路径、明确人工确认者、相关代码或素材改变后标为待复验。初版用简单 JSON 与 Markdown 导出即可，不必做后台系统。

**必须保留工作台与正式比赛的区别。** 工作台跳过正式金币、手牌、AI、兵线、倒计时及通用命令缓冲，因此“工作台通过”不能证明正式对局资格与网络同步通过。它应该记录自己验证了什么，也明确没验证什么。[S15]

### 少增加文档，多增加明确交付合同

现有 AGENTS、任务导航、新卡清单已经覆盖不少约束，不建议再添加多份相似规范。建议每个任务附一张短合同，由 AI 在动手前填写已知项，在结束时填结果：

```text
任务 ID / 基线提交 / 工作区状态：
用户可见目标：
必须保持不变的规则：
允许修改的模块与资源：
可能涉及的规则决策：
自动验证命令、结果与日志：
需要用户操作的验收场景：
人工确认记录及证据：
仍未验证或已知风险：
回滚方式：
```

“AI 已完成代码”“自动测试通过”“用户已确认手感/音频”是三种不同状态。任何工具生成截图或录音，都不能自动变成用户已经目视或试听通过。

### 给 AI 的改动范围需要是结构化的

纯数值任务只应触及定义和必要文档/测试；纯模型、卡面或音频替换不应改真实碰撞和伤害；新机制应指出复用点及新增的唯一主要职责模块。出现跨出允许范围的必要修改时，AI 应先说明原因和影响，而不是悄悄完成整轮重构。

并行开发应按文件/模块所有权划分。多个 Agent 同时改 Main、Unit 和通用动画状态机是高风险安排；卡牌素材可并行，共享机制的修改应独立集成。每个可回滚任务使用独立分支或工作树，合并后重新跑跨模块测试。这是建议流程，不是对历史开发方式的推断。

## 10. 性能审查：可识别风险，不伪造实测

### CL-12：重点不是“再优化一些”，而是建立预算与可重放场景

| 路径 | 已确认的结构事实 | 建议先测什么 | 测量支持后的动作 |
| --- | --- | --- | --- |
| 移动/碰撞 | 每单位避让扫描全体，接触使用全量两两遍历 | 单 Tick 耗时随单位数增长 | 空间桶/网格与稳定排序，保留精确窄相位 |
| 索敌/地形查询 | 多处通过 combatants 集合筛选、重复查询 | 调用次数与候选数量 | CombatantRegistry、按队伍/空地/结构分类的查询接口 |
| 固定时钟 | 一次 advance 可把全部积压 Tick 跑完 | 积压量、最长单渲染处理时间 | 有预算的赶帧、保留积压、明确过载策略 |
| 模型生成/变形 | 实例化与每实例动画库深复制 | 首次和批量生成峰值、内存 | 精准预备、有限预实例化或重用；保证可变资源隔离 |
| 音频 | 缓存、播放器池和持续层已经存在 | 同时播放数、淘汰数、首次音频峰值 | 类别预算与优先级，不是无限扩池 |
| 快照 | 数组构建、序列化和压缩 | 字节量、压缩耗时与端到端延迟 | 在实际数据支持下量化、变化掩码或压缩策略 |
| 渲染 | 独立 3D 视口持续更新 | 真机 CPU/GPU 帧耗时、透明叠加 | 按瓶颈调分辨率/特效预算/更新策略 |

这些不是已经测出的瓶颈排名。Godot 官方也区分持续低帧、间歇尖峰和加载慢，并强调应在目标硬件上用测量指导优化。[G03]

`MatchResources` 已做递归依赖预备并持有资源强引用，不能再声称项目完全没有预加载；它也明确不消除实例化成本。[S40]

固定时钟不能用“超过若干步就清空累计时间”来掩盖过载，这会改变时间与战斗语义。每帧工作预算只能限制一次渲染被阻塞多久；持续算力不足仍要降低负载或按明确策略处理，不能凭预算自动消失。

### 建议的基准场景

保留已有 32/64/128 单位逻辑采样，另加完整对局、双桥拥挤、批量生成/变形、持续范围技能叠加、有音频与无音频/完整与简化表现的对照。固定输入、初始状态、随机种子与运行版本，才能比较优化前后。[S11]

每次记录总帧耗时与 P95/P99、最大帧尖峰、模拟 Tick 耗时、积压、资源内存、实例数、声音数与快照流量。目标帧率和单位规模先由产品目标设定；本报告不凭空给项目承诺某台手机可跑多少单位。

## 11. 发布、平台与素材规范

### CL-14：明确“开发机可运行”之外的可复现性

`project.godot` 的 feature 标签包含 4.7 与 Forward Plus，而实际 rendering_method 是 gl_compatibility；README 的要求又较宽。这是配置与说明需统一的问题，不应据此宣称游戏真的同时运行两个渲染器。需要记录实际验证的引擎完整版本与模板版本。[S41][S01]

`.gitignore` 目前忽略整个 `export_presets.cfg`。Godot 官方区分可进入版本管理的导出预设与应保密的 `.godot/export_credentials.cfg`。建议审查并提交不含秘密和不必要本机路径的预设；凭据保持在仓库外。不要为了可复现把签名密钥或密码一起提交。[S42][G02]

正式面向手机之前，应建立 Android/iOS（按实际目标选择）的导出与设备检查：触屏交互、不同长宽比、安全区、后台/恢复、音频中断、联网权限、资源压缩、持续运行温升、内存与长局稳定性。720×1400 的竖屏配置本身不能证明这些已经通过。[S41]

素材目录已有英文命名、源件/包装分离、来源清单和 `.gdignore` 边界，应继续沿用。不凭资源哈希自动删重复文件，不把所有 source 目录一律忽略，也不把未立项队列直接变为运行时依赖。[S43][S16]

发行前另做素材使用与分发权限清单，区分原创代码、第三方模型、音频、图像、字体及来源；本报告没有对具体素材作授权或法律结论。

## 12. 建议执行路线与完成条件

| B1 | 纯表现不改规则 | CL-01 | 显式权威弹体几何；原行为不变；纯表现变体测试通过 |
| B2 | 实体生命周期同步 | CL-02 | Spawn/快照/销毁/重同步乱序收敛；上一局消息不污染下一局 |
| B3 | 终局统一收尾 | CL-03 | 双端可靠终态一致；战斗持续声与遗留效果按策略结束 |
| B4 | 会话与命令事务 | CL-04、CL-05 | 身份/阶段合法；重复注册无副作用；占位预留与失败路径一致 |
| C | 结构收敛 | CL-06、CL-07、CL-08 | 先抽会话/网络薄适配和工作台，再处理状态所有权；配置错误能清楚诊断 |

每个 P1 建议独立提交或小 PR，先增加能够揭示问题的回归，再做最小修复。不要把音效更新、平衡调整、目录重命名与网络修复揉在同一个“大重构”里。

C 阶段的最优先目标不是文件数量，而是让 Main 不再成为每个系统互相访问内部状态的通道。每抽取一块，应能独立描述输入、输出、状态所有者、生命周期和对应测试。如果新模块仍需要完整 Main 才能工作，要检查是否只是代码搬家。

## 13. 审查完成后的明确结论

**继续维护这个项目是合理的，现有投入值得保留；但下一轮应以工程收敛为主，而不是在共享核心中继续无约束叠加功能。**

对当前协作方式，最重要的不是要求用户学会逐行审代码，而是让项目本身回答四个问题：这次改了什么；不该变的规则是否没变；哪些结果经过自动或人工验证；后来什么修改使旧验收需要重做。

达到“新卡主要改自己的内容，通用机制改动有稳定边界，异常联机顺序能够恢复，验收结论可以追溯”之后，后续推进会比单纯再拆几十个文件更顺畅。
