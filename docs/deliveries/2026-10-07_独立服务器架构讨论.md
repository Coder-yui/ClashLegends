# 交付合同：独立服务器架构讨论

- **需求 / 来源**：用户对话；先明确两个客户端与独立权威服务器的职责，规划改造并讨论。
- **完成结果**：完成当前实现静态核对，提出以下讨论方案；没有修改运行代码，方案尚待讨论确认。
- **验证**：基线 `6998fd64`，开始时工作区干净。核对 Main、MatchSession、NetworkSnapshotSystem、BattleContext 与 Unit；本轮不执行机制或联网运行验收，不宣称改造已通过。
- **查看方式**：直接查看本文及对话。
- **遗留 / 未验证**：首期部署范围、断线规则与离线入口待确认；独立服务器、三进程测试及实际客户端表现均未实现或验证。

## 当前结构

已有主机权威 20Hz 模拟、命令验证、快照与生命周期屏障。主要耦合是 Main 同时承担权威模拟、玩家界面、资源准备及 RPC；MatchSession 只绑定一个对手；客户端固定阵营 1；快照与表现通知只发送给唯一对手。独立服务器不能仅以 headless 启动现有 host 代替。

## 职责建议

服务器拥有两名玩家的身份映射、卡组验证、手牌与费用、命令排程、寻路碰撞、伤害状态、实体生命周期、比赛时间及胜负。固定 20Hz，保留积压，不静默丢 Tick。服务器产生表现事件描述，不加载模型池或播放声音。

客户端拥有输入、相机、UI、资源预热、模型、动画、特效与音频；仅显示权威副本，可进行输入预检及待确认反馈，不推进权威状态。服务器分配阵营，客户端统一根据 local_team 转换视角与输入坐标。

共享现有规则定义、协议与通用逻辑类型；运行时状态互不共享。服务器负责核验客户端请求。将连接身份与阵营分开，按玩家维护请求序号。公共战场信息发给两端，手牌、牌序、未公开成长及请求结果按接收者投影。

## 分阶段建议

1. 明确首期为一服一局、两个客户端；定义连接、卡组、加载、运行、终局、清理生命周期，以及身份与消息契约。
2. 将本地玩家阵营与运行角色解耦；集中两队玩家状态，消除客户端必为阵营 1 的假设。
3. 提取独立战斗运行装配，保留通用 Unit、BattleContext 和领域系统；切断 UI、音频、模型池依赖，审计 Unit/Tower 的表现初始化与资源闭包。
4. 建立双玩家会话、统一请求入口、按接收者快照与事件分发；使用稳定一致的 RPC 节点路径，提升协议版本。客户端提交的 Tick 仅作参考，服务器约束排程范围。
5. 建立独立 server/client 启动入口，完成等待两端就绪、终局、断线与清场；保留单机及工作台对同一战斗核心的复用。
6. 将现有双进程验证升级为服务器加两客户端；覆盖阵营互换、请求去重与越权、隐私投影、慢加载、断线、重开、乱序及终局一致性，补充延迟/丢包条件和两端实际渲染、试听。

首期建议复用 Godot/GDScript 战斗逻辑与 ENet，不同时引入匹配、账号、数据库、多房间或断线续接。后续多房间需处理全局 combatants 查询等场景隔离问题。
